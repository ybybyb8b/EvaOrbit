# Memory Graph B0 / B1

This contract concerns code and isolated tests. It does not mean production was migrated,
deployed or accepted by the user. Migration must be deployed with the matching server;
the old direct-write client contract is intentionally retired.

## Safety

The internal AI tool loop receives no recalled Graph text. A final answer-only request
receives a separate JSON user message containing selected facts and source identifiers.
JSON escaping plus escaped angle brackets/control characters preserves the original
values on decoding. Memory never appears in the system message. The final request has
no tools and returned tool calls are never dispatched. These are enforceable application
boundaries, not a guarantee about a model's wording or factual correctness.

SQLite is local single-owner development storage. npm run dev binds 127.0.0.1;
the proxy fails closed without the launcher marker, in production/hosting, or for
non-loopback Host/Origin, foreign forwarding and cross-site requests. Headers alone
cannot establish a local TCP peer: the controlled listener is part of the contract.
Do not expose it through tunnels/proxies. Remote previews use dev:online and Supabase.

## MCP

There are still eight generic tools. The new resource is memory_candidate:
- eo_search filters: status, proposed_by, promoted_fact_id; no keyword search or pagination.
- eo_get reads a known Candidate UUID.
- eo_action submit accepts fact, sources, review_mode, written_by, request_id,
  proposed_by and proposer_model.
- Ordinary promote/reject is Web-only; MCP does not advertise or accept those actions.
- eo_create(memory_fact) returns a migration error pointing to Candidate submit.
- eo_update(memory_source) now accepts source_record_id in addition to URL/excerpt/note.

Example: model inference remains pending.

~~~json
{
  "resource": "memory_candidate",
  "action": "submit",
  "data": {
    "review_mode": "manual",
    "request_id": "<stable request UUID generated before the first call>",
    "proposed_by": "model",
    "proposer_model": "actual-model-name",
    "fact": {
      "subject_entity_id": "<resolved Entity UUID>",
      "predicate": "prefers",
      "object_value": "tea",
      "epistemic_type": "derived"
    },
    "sources": [{"source_resource": "chat", "excerpt": "<original words>"}]
  }
}
~~~

Example: explicitly stated/corrected user fact, completed in one call.
Use a real UUID and keep it for retries. Add supersedes_fact_id inside fact only
when correcting an incorrect assertion of the same subject/predicate/perspective.

~~~json
{
  "resource": "memory_candidate",
  "action": "submit",
  "data": {
    "review_mode": "user_confirmed",
    "written_by": "<declared writer>",
    "request_id": "<stable request UUID>",
    "fact": {
      "subject_entity_id": "<resolved Entity UUID>",
      "predicate": "prefers",
      "object_value": "coffee",
      "epistemic_type": "direct_statement"
    },
    "sources": [{"source_resource": "chat", "excerpt": "<user's exact statement>"}]
  }
}
~~~

user_confirmed is a caller declaration, not a verified signature or independent proof
of the user's words. It requires direct_statement, proposed_by=user (the default for
this mode), written_by, request_id, and a chat Source with the original excerpt.
manual defaults proposed_by=model and never automatically promotes. Every MCP submit,
including manual inference, requires a valid request_id generated by the client before
the first call. Reuse that ID for retries, including after a lost response. The existing
Web POST retains its optional-ID compatibility; callers of that endpoint must supply a
stable request_id themselves if they need lost-response retry safety.

## Shared transactions and audit

Web POST /api/memory-graph and MCP submit call the same service. Web PATCH candidates/:id
uses the existing review path; ordinary MCP promote/reject is disabled. Candidate terminal states remain
promoted and rejected.

The MCP boundary is enforced, not inferred from model instructions: review actions are
absent from discovery and rejected by the registry. The service also refuses reviews
while an MCP request context is active, regardless of supplied audit labels. PostgreSQL
review RPC additionally requires the signed JWT audience to be authenticated (scalar or
a singleton array) and client_id to be absent. An MCP/OAuth JWT or missing claims fails
closed even if p_client says web. A Web session is the trusted review authorization;
these checks do not prove that a human clicked a button. Local SQLite review uses the
existing controlled-loopback Web boundary.

SQLite uses BEGIN IMMEDIATE. PostgreSQL submit/review RPCs serialize lifecycle changes
per owner with a transaction advisory lock, lock referenced Entities and the corrected
Fact, and reuse the private promotion/write functions. No direct authenticated
Fact/Candidate inserts, status edits or legacy write RPC executions remain.

user_confirmed creates the candidate, Fact, Sources, correction edge, predecessor
invalidation, review result and audit within one transaction. Manual promotion performs
the same validation and writes, while the previously created pending candidate remains
pending if promotion fails. Any error rolls back the operation.

Candidate stores written_by, actor, client, request_id, review_mode and review_client,
alongside existing proposer, model, creation/review timestamps and promoted_fact_id.
actor is the authenticated owner (local for SQLite); written_by is caller-declared.
Web/MCP routes assign their client label, using the verified OAuth client_id when present,
otherwise mcp. These labels are audit metadata, not independent user confirmation.
Legacy rows retain null audit fields; no historical attribution is invented.

A unique (owner, request_id) rejects reused IDs with different submission content/client.
Identical replay returns the existing candidate, even after its Fact was corrected.
RPCs return the written Candidate directly, avoiding a separate write-then-read request.
If a response is lost, replay submit with identical content/request_id or get the known
Candidate after a manual review. Never blindly generate a new request_id to retry.

Formal Fact -> memory_candidate search promoted_fact_id -> original submission and review
audit. No separate audit table or duplicated audit fields on every resource are needed.

## Sources

chat requires a nonblank original excerpt. Non-chat resources require a record ID or
HTTP(S) URL; an excerpt helps locate the evidence but does not replace that reference.
note is supplemental. Source resource names keep their existing meaning and remain open.

PATCH preserves omitted values exactly, including empty strings, NULL, and whitespace
in legacy records. Both repositories trim submitted IDs, URLs and notes, preserve
nonblank excerpts verbatim, and treat submitted empty strings as NULL. The PostgreSQL
trigger validates SQL values as supplied.
Both backends use ECMAScript trim whitespace for Source checks, including U+FEFF.
Source input rejects NUL. SQLite backup restore checks for NUL while preserving
legacy field values.

Both backends validate new Sources in full. When evidence changes, they check the
changed fields and require the resulting record to have the evidence its resource
requires. An omitted legacy field may keep its old format. A note-only change skips
evidence validation. The original table constraint still rejects clearing the only
non-NULL field on a Source.

SQLite checks last-source deletion inside its write transaction. PostgreSQL removes
direct delete permission and uses delete_memory_source: it touches/locks the parent Fact
row before checking remaining valid evidence and deleting. The row-version touch also
forces a serialization failure for conflicting stale-snapshot transactions.
Deleting a Source never deletes its Fact. Restore requires valid evidence.

## Corrections and real change

A correction requires an active old Fact with the same subject, exact predicate and
perspective (null is its own value). Self-reference and existing successors are rejected.
Old Sources and all versions remain. Restore checks both complete predecessor and successor
chains, not only the immediate successor, and refuses another active version in that chain.

For a fact that used to be correct and later changed, explicitly PATCH the old valid_to
and submit a new candidate without supersedes. Do not invalidate true history.
These remain separate operations in B1; there is no automatic date inference or atomic
real-world transition API. Inclusive dates cannot represent some same-day or uncertain
boundaries; those await Phase D. No cardinality or semantic predicate reasoning is added.

  path. Use the supported backup/restore boundary; this phase does not expand that script.

## Scope

No production database was targeted by tests. PostgreSQL tests use isolated PGlite and
execute the actual migrations/functions as authenticated roles with RLS. SQLite uses
temporary databases and competing child processes for deletion. PGlite serializes its
connection; multi-session PostgreSQL lock contention still needs a separate staging test.

No memory_context, pagination, predicate registry, cardinality, scope, date precision,
Memo links, Drive matching, embeddings or stored-data cleanup is included.

## Focused follow-up: ordinary review authorization and MCP idempotency

Confirmed gaps in the original B1 implementation:
1. MCP manual submit followed by promote could create a formal Fact without an
   independently authorized ordinary review. The original transaction was atomic,
   but that did not establish review authorization.
2. manual submit could omit request_id. A generated server key is not recoverable by
   the caller after a lost response, allowing duplicate pending candidates on retry.

Minimal fixes:
- MCP exposes submit/search/get only; promote/reject remains in the existing Web UI/API.
- The service rejects ordinary review from trusted MCP request context, even if a caller
  passes a web client label. The label is audit metadata, not authorization.
- The new PostgreSQL migration adds a JWT guard before the existing review transaction.
  It does not change the transaction body, candidate states, Fact writes or version chain.
  Private promote/write functions remain unavailable to authenticated direct callers.
- MCP requires request_id for both manual and user_confirmed submission; registry and
  service enforce this. The existing (owner,request_id) uniqueness and payload comparison
  are reused: identical replay returns the same candidate; changed payload/client with
  the same key is rejected; a new key is a distinct request. No content hash, similarity
  deduplication or merge of unrelated facts is introduced.
- user_confirmed retains the original one-transaction path and its existing evidence,
  direct_statement and writer requirements. It remains caller-declared confirmation,
  not independent proof of what the user said.
- Web submit optional-ID behavior remains compatible and is not claimed to be
  automatically safe to retry after response loss.

Follow-up files: repositories/index.ts, services/memory-graph.ts, MCP registry/bindings/
action schemas/guidance/tool descriptions, the new PostgreSQL migration, related registry/
MCP/HTTP/PostgreSQL tests, and the corresponding Memory/MCP documentation. No new tables,
SQLite migration, pagination, predicate registry or recall feature is added.

Remaining runtime checks: apply the new migration only in an authorized isolated/staging
environment first, verify actual Supabase Web/OAuth JWT claim shapes and privileges,
and verify multi-session PostgreSQL behavior. No production deployment or migration
was performed. No automated check can establish that declared user_confirmed text
actually came from a human. The broader B0/B1 work and unrelated workspace edits remain.
